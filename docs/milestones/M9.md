# Milestone M9 — Digital signatures (v0.9)

**Goal:** signature verification you can trust, including detection of the published attack classes, then PAdES signing from B-B to B-LTA with software and hardware keys. Visual "fill & sign" signatures are offered and never confused with cryptographic ones. Plan reference: [`PLAN.md` §C, §H, §K](../PLAN.md) (phase 9), [ADR-0006](../adr/0006-crypto-backend.md). Estimated effort: 14–16 weeks. **Security correctness beats feature count:** verification ships first and must be right before signing is enabled.

**How to use this file:** the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md) and the [milestone rules](README.md#rules-for-every-milestone).

## M9 acceptance criteria

- [ ] Every sample of the published PDF signature attack classes in our test set (universal signature forgery, incremental saving attack, signature wrapping, shadow hide/replace/hide-and-replace, evil annotation and sneaky signature certification attacks) is flagged as invalid or modified, never shown as plainly valid.
- [ ] Valid signatures from Acrobat, other signing tools and our own verify as valid. The trust, revocation and timestamp status is shown separately from document integrity.
- [ ] Signatures created by Vellora at B-B, B-T, B-LT and B-LTA validate in Adobe Acrobat (manual) and in the EU DSS validation tool (automated, external tool).
- [ ] Software keys (PKCS#12), PKCS#11 tokens, Windows certificate store and macOS Keychain keys can sign. Private keys never enter the engine process.
- [ ] Network use (revocation, TSA) happens only when the user enables it, and only from the UI process (decision #4, ADR).
- [ ] Tagged pre-release `v0.9.0`, only if the maintainer asks.

## Phase A: verification

### - [ ] Task 1: Crypto backend and network ADRs
- **Do:**
  - ADR "OpenSSL integration": the `openssl` crate; vendored build on Windows and macOS, system OpenSSL 3 on Linux and Flatpak; FIPS not in scope; how CI and packaging get it. Update the dependency policy.
  - ADR "Network access for signatures": opt-in, UI process only, an HTTP client choice (license- and audit-checked), timeouts, size caps, no cookies, proxy support, and a visible indicator when used.
- **Acceptance:** ADRs merged. `cargo deny` passes with the new dependencies, and all three OS builds succeed.
- **Depends:** 0

### - [ ] Task 2: Signature data model
- **Do:**
  - In `doc`: signature fields and values:
    - `/Filter`, `/SubFilter` (`adbe.pkcs7.detached`, `ETSI.CAdES.detached`, `adbe.pkcs7.sha1` read-only, `ETSI.RFC3161` document timestamps)
    - `/ByteRange`, `/Contents`, `/M`, `/Reason`, `/Location`, `/Name`, `/Reference` (DocMDP/FieldMDP), `/Prop_Build`
  - DSS (`/Certs`, `/OCSPs`, `/CRLs`, `/VRI`).
  - Map each signature to the **revision** it covers. A ByteRange end must equal a revision end.
- **Acceptance:** corpus test reading every signed document with no panics. Unit tests for each sub-filter.
- **Depends:** 1

### - [ ] Task 3: Integrity verification
- **Do:**
  - **Strict ByteRange rules:**
    - exactly two ranges, starting at 0
    - the gap is exactly the `/Contents` hex string including its delimiters
    - ranges end at the end of the signed revision
    - no overlap, no negative lengths
  - Digest over the ranges (streamed). CMS parse and verify through OpenSSL: signed attributes (`messageDigest`, `signingCertificateV2`, content type), signature algorithm allowlist (RSA PKCS#1 v1.5 / PSS, ECDSA, EdDSA; MD5 rejected; SHA-1 shown as weak).
  - Result types distinguish *integrity* from *trust*.
- **Acceptance:** tests for every ByteRange violation (fixtures generated by our writer) and every algorithm. Valid fixtures from multiple producers verify.
- **Depends:** 2

### - [ ] Task 4: Trust, chain and revocation
- **Do:**
  - Trust anchors: the OS root store (Windows ROOT, macOS Keychain, the Linux CA bundle) plus user-imported anchors (stored in app data, with a management UI). Adobe AATL / EU Trusted Lists go to the backlog.
  - Chain building from embedded certificates, DSS and the store. Key usage and EKU checks for document signing.
  - Validity at signing time (when a trusted timestamp exists) or at the current time.
  - Revocation from embedded DSS/CMS data offline. **Online OCSP/CRL** only when enabled (task 1 ADR).
- **Acceptance:** tests with a generated test PKI (root, intermediate, leaf, revoked leaf, expired leaf, OCSP responder fixture).
- **Depends:** 3

### - [ ] Task 5: Timestamps
- **Do:** verify RFC 3161 tokens: signature timestamps (unsigned attribute) and document timestamps (`ETSI.RFC3161`), the TSA certificate chain, the message imprint, and the TSA's time used for validity.
- **Acceptance:** tests with generated TSA fixtures and real timestamped corpus documents.
- **Depends:** 4

### - [ ] Task 6: Modification analysis and attack detection
- **Do:**
  - For each signature, compare its signed revision with every later revision (object-level diff) and classify changes against DocMDP P (1/2/3) and FieldMDP locks. Allowed: form fill, annotations (P=3), signatures, DSS and timestamps. Anything else is flagged.
  - **Attack checks:**
    - overlays or annotations added after signing that cover signed content
    - changed objects referenced from the signed revision (shadow attacks)
    - xref/trailer tricks in later revisions
    - `/Contents` padding misuse
    - certification + approval misuse
  - **Visual check:** render the signed revision (open the revision prefix in a separate sandboxed engine) and the current revision, and run the M5 visual compare on pages with changes.
- **Acceptance:** the attack test set (task 8) is flagged 100%. Legitimate multi-signature workflows (sign → fill → countersign) are classified correctly.
- **Depends:** 5

### - [ ] Task 7: Signature panel and status UI
- **Do:**
  - Signatures panel with a status per signature:
    - valid
    - valid with allowed later changes
    - modified after signing (with a list of changes)
    - invalid
    - signer identity not trusted
    - revoked
    - not checked (revocation unknown)
  - Details: signer, claimed time vs timestamp time, reason/location, certificate chain viewer, revocation source, certification level, and **"View signed version"**.
  - A document banner for certified documents. The wording is reviewed for clarity, with no false reassurance.
- **Acceptance:** Qt tests per status. Wording snapshot tests. Manual checklist.
- **Depends:** 6

### - [ ] Task 8: Attack and interop test sets
- **Do:**
  - Collect the published attack sample files where their license allows, and generate our own fixtures for every class.
  - Collect valid signed samples (Acrobat, other OSS tools, ETSI-style samples).
  - Nightly job runs verification over them and asserts the expected verdicts.
- **Acceptance:** sets committed (manifest + licenses). Nightly green.
- **Depends:** 6

## Phase B: signing

### - [ ] Task 9: Keys and signers (UI process only)
- **Do:**
  - A `Signer` abstraction in the UI-side Rust client, never in the engine:
    - PKCS#12 file + password (zeroised, not stored)
    - PKCS#11 module path + slot + PIN (`cryptoki`)
    - Windows certificate store (CNG, incl. smart cards)
    - macOS Keychain (Security framework)
  - Certificate picker UI filtered for document-signing usage.
- **Acceptance:** tests with SoftHSM (PKCS#11), a PKCS#12 fixture, and the Windows/macOS stores on their CI runners using test certificates.
- **Depends:** 1

### - [ ] Task 10: Signing flow, PAdES B-B and certification
- **Do:**
  - Protocol:
    - `PrepareSignature{field | new rect, appearance, level, certify?}`: the engine reserves `/Contents` (size estimated from the chain + timestamp + revocation data, with a retry at double size if too small), writes the incremental update into the output handle, and returns the **ByteRange digest**
    - the UI's Signer produces the CMS (CAdES-detached, `signingCertificateV2`, no `signingTime` per PAdES; the time goes in `/M`)
    - `EmbedSignature{cms}`: the engine writes the hex into the reserved space
  - Appearance: name, date, reason, location, optional logo, drawn/typed/imported handwriting image, "Digitally signed by …".
  - Certify (DocMDP P=1/2/3) and lock fields (FieldMDP).
  - Signing is **always incremental**.
- **Acceptance:** our B-B signatures verify in Vellora, the EU DSS tool (CI, external) and Acrobat (manual). Existing signatures stay valid after countersigning.
- **Depends:** 9, 3

### - [ ] Task 11: B-T, B-LT, B-LTA and "Add LTV"
- **Do:**
  - B-T: a signature timestamp from a configured TSA (opt-in network).
  - B-LT: add DSS with certificates, OCSP responses and CRLs (fetched online when enabled, or supplied) and VRI.
  - B-LTA: a document timestamp after B-LT.
  - Op `AddLongTermValidation` for existing signatures.
- **Acceptance:** each level validates as that level in the EU DSS tool (CI). An offline mode clearly reports what it couldn't add.
- **Depends:** 10, 5

### - [ ] Task 12: Fill & Sign (visual signatures)
- **Do:**
  - A visual-only tool: typed, drawn or image signature, initials and date stamps, saved as stamp annotations or flattened content.
  - Saved signature images live in app data (user-deletable).
  - The UI **always** labels these "not a digital signature".
- **Acceptance:** Qt tests. The label is present in every entry point (test enumerates them).
- **Depends:** 7
