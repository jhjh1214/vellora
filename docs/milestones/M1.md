# Milestone M1 — Viewer (v0.1)

**Goal:** a daily-usable, fast, safe PDF viewer. Plan reference: [`PLAN.md` §K](../PLAN.md) (phase 1) and the viewer feature list in §J. Estimated effort: about 8 weeks for one developer. Roadmap: [`roadmap.md`](../roadmap.md).

**How to use this file:** follow the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md).
- Take the first unchecked task whose dependencies are checked.
- Implement only its scope and pass its acceptance checks plus the standard checks.
- Tick it, and add `Note:` lines for the next session.
- If a task proves much larger than described, split it here (e.g. 3a, 3b) before implementing.

This file is the hand-off between sessions. Notes go directly under the task they belong to.

**Standard checks** (implied by every task):
`cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace && cargo deny check`, plus for `app/`: the CMake build, `clang-format --dry-run -Werror` and the Qt tests.

## M1 acceptance criteria (from the plan)

- [ ] Viewing performance targets in [`performance-targets.md`](../architecture/performance-targets.md) are met and measured by `cargo xtask bench`.
- [ ] The engine opens ≥ 98% of corpus v0 (password-protected files excluded) and the UI process never crashes on the malformed/malicious subset. The M0 corpus test (`crates/engine/tests/corpus.rs`) is the gate.
- [ ] Encrypted documents open after a password is entered; a wrong password never crashes and never reveals content.
- [ ] A rendering regression suite (golden pixels) runs in CI on all three OSes.
- [ ] The UI watchdog reports no stalls caused by our code during scrolling, zoom and search (frame time is measured; see task 1).
- [ ] Tagged pre-release `v0.1.0` (only if the maintainer asks).

Carry-overs from M0 that this milestone must close: password path (task 2), frame-time measurement instead of loop-blocking (task 1), macOS `tst_canvas_render` hang (task 1), lazy-repair decision `ObjectStore::settle` at open (task 3), cold-cache and Linux/macOS benchmark numbers (task 12).

## Phase A: robustness carried over from M0

### - [ ] Task 1: Frame-time watchdog and macOS canvas test
- **Goal:** the UI-responsiveness check measures what our code controls.
- **Do:**
  - Replace "event loop blocked > 16 ms" by a measurement that excludes the vsynced present: time spent in our handlers and in `CanvasWidget::render()` per frame, with a counter and a log line above a threshold.
  - Find out whether the macOS `tst_canvas_render` hang is the runner or the present path; re-enable the test there or document why not.
- **Acceptance:** 10,000-page scripted scroll and zoom shows no frame over budget from our code on Windows and Linux CI; macOS decision recorded.
- **Depends:** —

### - [ ] Task 2: Password path
- **Goal:** open encrypted documents.
- **Do:**
  - Extend the IPC `Open` flow with an optional password; the engine tries it through `cos` decryption and hands PDFium the same password.
  - Typed answers for "password required" and "wrong password" (they exist as errors today); the UI shows a modal prompt, three attempts, no password is logged or stored.
  - `vellora inspect --password` stays as is.
- **Acceptance:** the 10 password-protected corpus files open with their known passwords in a test; wrong password gives the typed error and no crash.
- **Depends:** —

### - [ ] Task 3: Settle at open and show repairs
- **Goal:** close the lazy-repair gap noted in M0 task 13.
- **Do:**
  - The engine calls `ObjectStore::settle()` (make it public) at open, so page count and the saved document agree.
  - Report `repaired` reasons to the UI; show a non-modal "this file was repaired" notice and list reasons in a details view.
- **Acceptance:** `duplicate-object-after-bad-offset.pdf` shows the same page count before and after a rewrite; the notice appears for repaired corpus files.
- **Depends:** —

## Phase B: viewing

### - [ ] Task 4: View modes, fit modes and rotation
- **Do:** continuous, single page and two-up layouts; fit width, fit page, actual size; view rotation (not written to the file); remember per-window state.
- **Acceptance:** layout unit tests (page positions for each mode); 10,000-page document scrolls in every mode within the performance targets.
- **Depends:** 1

### - [ ] Task 5: Thumbnails sidebar
- **Do:** low-priority tile requests for thumbnails, cache budget, current-page highlight, click to jump, keyboard navigation.
- **Acceptance:** thumbnails never delay visible tiles (scheduler test); the sidebar is usable on the 10,000-page document.
- **Depends:** 4

### - [ ] Task 6: Outline (bookmarks) and page labels
- **Do:** read `/Outlines` and `/PageLabels` in `cos` (cycle-safe, bounded), expose through the engine protocol, tree view with lazy expansion, jump to destination.
- **Acceptance:** corpus run with no panics (including `pdfium-bookmarks_circular`); destination types `/XYZ`, `/Fit*` resolved.
- **Depends:** 3

### - [ ] Task 7: Links
- **Do:** link annotations and named destinations: internal jumps; external URIs shown to the user and opened only after confirmation; Launch, JavaScript and GoToR actions never run (invariant 8).
- **Acceptance:** tests for each action type; URI confirmation shows the full target; no network access from the engine.
- **Depends:** 6

### - [ ] Task 8: Text extraction and selection
- **Do:** page text with character boxes through the engine (PDFium text page), selection by mouse and keyboard, copy, reading order fallback, RTL and ligature cases.
- **Acceptance:** selection rectangles match golden boxes on a fixture set; copy output compared with an independent extractor on a corpus subset.
- **Depends:** 4

### - [ ] Task 9: Search
- **Do:** find in document (case, whole word), results list with context, highlight on the canvas, incremental and cancellable, runs in the engine at low priority.
- **Acceptance:** search on the 10,000-page document returns the first hit in under 1 s and stays cancellable; UI watchdog clean while searching.
- **Depends:** 8

## Phase C: inspection and CLI

### - [ ] Task 10: Inspector v1 and security report
- **Do:** read-only panel built on `vellora-inspect`: document properties, revisions, encryption, repairs and the risky-feature list (JavaScript, launch, embedded files, XFA, signatures) with plain-language explanations; export as JSON.
- **Acceptance:** the panel shows the same data as `vellora inspect --json` on the corpus; no PDF parsing in the UI process (data arrives over IPC).
- **Depends:** 3

### - [ ] Task 11: CLI `security` and `render`
- **Do:** `vellora security <file>` (risk summary, exit codes for scripts) and `vellora render <file> --page N --scale S -o out.png`, both using the engine process; documented in `docs/user/cli.md`.
- **Acceptance:** CLI tests with fixtures and snapshot tests; `render` output matches the golden image within the existing tolerance.
- **Depends:** 2, 10
