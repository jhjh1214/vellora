# Milestone M1 — Viewer (v0.1)

**Goal:** a fast, safe PDF viewer you could use every day instead of the one you have now. Plan reference: [`PLAN.md` §J, §K](../PLAN.md) (phase 1). Estimated effort: 10–12 weeks for one developer.

**How to use this file:** follow the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md) and the [milestone rules](README.md#rules-for-every-milestone).

**Standard checks** (implied by every task):
`cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace && cargo deny check`, plus for `app/`: the CMake build, `clang-format --dry-run -Werror` and the Qt tests (`ctest`).

**Protocol rule for this milestone:** several tasks extend `vellora-ipc`. Every change to `Request`/`Response` bumps `PROTOCOL_VERSION`, keeps `Hello` frozen, adds round-trip and validation tests in `crates/ipc`, and enforces size caps on any new variable-length field.

## M1 acceptance criteria

- [ ] Viewing performance targets in [`performance-targets.md`](../architecture/performance-targets.md) marked "Phase 1" are met on Windows and Linux and measured by `cargo xtask bench`. macOS is measured and recorded but not enforced until M6.
- [ ] The engine opens ≥ 98% of corpus v0 with password-protected files **included** (their passwords come from the corpus manifest). The UI process never crashes on the malformed subset. Gate: `crates/engine/tests/corpus.rs`, run nightly in CI.
- [ ] Encrypted documents open after a password is entered. A wrong password never crashes and never shows content.
- [ ] The engine runs inside an OS sandbox on Windows and Linux. Each gap in the security model's "Sandbox status tracker" for those two platforms is closed or has a written reason and a milestone.
- [ ] A rendering regression suite (golden pixels) runs in CI on all three OSes.
- [ ] Frame-time measurement shows no frame over budget caused by our code during scripted scroll, zoom, thumbnail browsing and search on the 10,000-page document (Windows and Linux CI).
- [ ] Every user action is reachable by keyboard and listed in the command palette. The canvas exposes text and links to screen readers (NVDA on Windows and Orca on Linux, checked by hand with a written checklist).
- [ ] Installable artifacts for Windows and Linux (Flatpak) are built by CI and published as nightly pre-releases. A macOS `.dmg` is built for testers (unsigned).
- [ ] Tagged pre-release `v0.1.0`, only if the maintainer asks.

### - [x] Task 2: Client-side deadlines and file write-deny
- **Goal:** close three gaps in the security model: no deadline on handshake/`Open`, no UI-side kill of a stuck tile, other processes truncating the mapped file.
- **Do:**
  - In `crates/engine-client`: deadlines for `Hello` and `Open` (default 10 s and 30 s; configurable in `ClientConfig`). On expiry, kill the engine and report a typed `EngineTimeout`.
  - A UI-side watchdog that kills the engine when a tile is more than 2× past its hard deadline without `TileReady` (the engine's own abort may not fire if the process is wedged).
  - Open the document with a sharing mode that denies writers where the OS allows: Windows `FILE_SHARE_READ` only. On Linux and macOS, use an advisory lock where possible, and detect modification (size and mtime check at each engine restart). Show a notice when the file changed on disk.
  - Update the gap table in `docs/architecture/security-model.md`.
- **Acceptance:** integration tests: (a) a test engine that never answers `Hello` is killed within its deadline and the UI gets `EngineTimeout`; (b) a simulated wedged tile is killed by the client; (c) on Windows, another process cannot open the document for writing while it's open.
- **Depends:** —
- Note: `EngineTimeout` is an `Event` (open is async) with a `Stage` (`Hello`/`Open`/`Tile`). Hello/Open are final (no restart, no `Failed`); a stalled tile is killed and goes through the normal crash and restart path.
- Note: Interpretation: the tile watchdog measures 2x the hard deadline from the engine's *last answer* while requests are in flight, not from each request, since a request can queue behind others.
- Note: Tests use `crates/engine-client/examples/fake_engine.rs` (built by `cargo test`). Windows: the writer test and the Qt app were run locally; the Unix advisory-lock and `DocumentChanged` tests only ran in CI.
- Note: Linux/macOS cannot deny writers (advisory `flock` only): size, mtime and (Unix) inode of the handle and the path are compared at each engine restart and reported as `DocumentChanged`. Gap table updated.
- Note: Windows' `FILE_SHARE_READ` also blocks rename and delete of the open file; M2's atomic save must account for it (`docs/backlog.md`).

### - [x] Task 3: Bound the recovery scan budget in `cos`
- **Goal:** close the CPU-exhaustion gap from M0 task 5. A file with thousands of broken stream lengths must not cost thousands of full-file scans.
- **Do:**
  - Add a per-document scan budget to `cos::limits::Limits` (e.g. total bytes scanned for `endstream` ≤ 4× file size, minimum 64 MiB). Charge every `endstream` search and recovery rescan against it.
  - When it's exhausted, return a typed `LimitExceeded` for that object only. The document stays open.
  - Add a fuzz regression fixture (generated in the test) with 10,000 streams with wrong `/Length`.
- **Acceptance:** the generated fixture opens in < 2 s with the budget enforced (asserted with a generous CI timeout). The existing corpus tests and the invariant harness are unchanged.
- **Depends:** —
- Note: `ScanBudget` (new `Limits::min_scan_bytes` 64 MiB, `scan_bytes_per_file_byte` 4; `LimitKind::ScanBytes`) is per `ObjectStore`, charged by `Parser::with_scan_budget` for every `endstream` search, including `/Length` lookups. A search cut short by the budget is `LimitExceeded` for that object; the store stays open.
- Note: Deviation: the recovery rebuild (`recovery::scan_objects`) is not charged to it. It keeps its own work budget (4x file size + 1 MiB, from M0 task 8), runs at most twice per store, and is already bounded.
- Note: Test in `crates/cos/tests/fuzz_regressions.rs`: 10,000 streams with a wrong `/Length` and no `endstream` (about 7 GB of scanning unbudgeted). Budgeted: 0.35 s for the file; with the budget lifted the same test fails (27.7 s debug).
- Note: Locally `qpdf` is missing, so `qpdf_accepts_every_writer_output` and `object_counts_match_qpdf_show_xref` fail here; the other `cos` corpus tests (`--ignored`) pass.

### - [x] Task 4: Windows sandbox for the engine
- **Goal:** the engine runs with the least privilege Windows offers.
- **Do:**

  - Run the engine in an **AppContainer** with no capabilities (no network, no user files). If PDFium's font enumeration or the inherited handles fail inside it, fall back to a restricted token + low integrity level, and record why in an ADR.
  - Check that PDFium still finds system fonts (`C:\Windows\Fonts`), and that inherited handles (document, tile region, stdio) work.
  - Add a test that the sandboxed engine cannot open a file in the user's profile, cannot create a socket, and cannot start a child process.
  - Write an ADR "Engine sandbox on Windows" with the measured outcome. Update the tracker.
- **Acceptance:** the three negative tests pass on Windows CI. The corpus gate still passes at the M0 level, run sandboxed.
- **Depends:** 2
- Note: `AppContainer` (no capabilities; its profile is registered on first use, as a clean machine needs) in `engine-client/src/sandbox.rs`; handle list; created suspended, jailed, resumed; fail closed. The restricted-token fallback was not needed (ADR-0017).
- Note: Deviation: "cannot create a socket" is not achievable, as a container can still create and bind one. The test asserts that TCP connects and UDP datagrams to the loopback never arrive; evidence in ADR-0017.
- Note: Gotchas: `CreateProcess` fails in a container without `LOCALAPPDATA` in its environment; the launcher gives the container a file-level read ACE on the engine and on PDFium (`$VELLORA_PDFIUM_LIB`, else next to the engine). `take_stdin`/`take_stdout` now return `File`.
- Note: Task 23: the installed engine and `pdfium.dll` must be readable by `ALL APPLICATION PACKAGES` (default under `Program Files`); a per-user install relies on that grant; the uninstaller should call `DeleteAppContainerProfile("Vellora.Engine")`. A start costs about 13 ms more (19 vs 6 ms).

### - [x] Task 5: Linux sandbox for the engine
- **Goal:** the same on Linux.
- **Do:**
  - Back the tile region with a **sealed `memfd`** (`F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_SEAL`), closing the "engine can shrink the region" gap.
  - After startup (PDFium loaded, fonts enumerated), apply **Landlock** (read-only access to font directories only, or nothing if PDFium has already enumerated them), `PR_SET_NO_NEW_PRIVS`, and a **seccomp-bpf** allowlist (no `execve`, no `fork`/`clone` of processes, no `socket`, no `open` of new paths except via Landlock).
  - Evaluate crates (`landlock`, `seccompiler`, `extrasafe`) against the dependency policy. Choose in an ADR "Engine sandbox on Linux".
  - When the kernel lacks Landlock, degrade with a logged warning, never a failure to open.
  - Flatpak note: inside the Flatpak sandbox, seccomp filters stack. Test the Flatpak build in task 23.
- **Acceptance:** negative tests (no file outside the allowed set, no socket, no exec) pass on Linux CI. Corpus gate unchanged.
- **Depends:** 2
- Note: Self-sandboxing engine (`crates/engine/src/sandbox.rs`, called in `main` before the PDFium thread): Landlock (reads of fonts, libraries, the PDFium directory, `/proc/self`) plus seccomp; `landlock` and `seccompiler` chosen in ADR-0018. The tile region is a sealed `memfd`.
- Note: Deviation: the seccomp filter is a deny list, not an allow list, and the sandbox is applied before PDFium loads (its directory stays readable). Reasons in ADR-0018; tightening is in `docs/backlog.md`.
- Note: Landlock or seccomp missing on a kernel gives a `warn` log, never a failed open. The Linux CI test requires `landlock: Full`, so a runner without Landlock would fail it instead of passing quietly.
- Note: Verified only in CI (Linux code was written on Windows): the probe test, the engine, client and Qt suites, the seal test. Not run on Linux: the corpus gate and a font comparison. Task 23: check the filters inside Flatpak.
- Note: Gotcha: two packages must not share an example name: `engine` and `engine-client` both had `sandbox_probe`, the builds overwrote one another's binary and CI failed at random with an empty report. The engine one is `engine_sandbox_probe`.

### - [ ] Task 7: Password path
- **Goal:** open encrypted documents.
- **Do:**
  - Extend `Open` with an optional password (zeroised after use with the `zeroize` crate). The engine tries it through `cos` decryption and gives PDFium the same password.
  - Typed answers: `PasswordRequired`, `WrongPassword`. The UI shows a modal prompt with three attempts and never logs or stores the password.
  - Owner-password-only files (permissions without a user password) open normally. Permissions are shown in the Inspector (task 18) and not otherwise enforced in a viewer, except that **printing honours the print permission bit** (task 16) with a visible explanation.
  - Add a `password` field to the corpus manifest for the 10 protected files, and let the corpus gate use it.
- **Acceptance:** all protected corpus files open with their passwords in the gate. A wrong password gives the typed error and no crash. A test asserts that the password never appears in logs at any level.
- **Depends:** 6
- Note: Everything in *Do* is implemented and tested, and two of the three acceptance sentences hold. **The box stays unchecked** (Decisions needed #7): of the 10 files the gate counted as protected, 8 open with their manifest passwords, but `pdfium-encrypted_hello_world_r2_bad_okey` and `_r3_` have a broken `/O` (`cos` refuses the dictionary, PDFium refuses every password), so no password opens them. They stay in the gate as typed refusals, without a `password`. Tasks 8 and later do not depend on this.
- Note: Protocol v3: `Open { handle_token, password: Option<Password> }` (UTF-8, at most 256 bytes, no NUL, redacted `Debug`, wiped on drop); `ErrorKind` gains `PasswordRequired` and `WrongPassword`. `Client::submit_password` answers them (the engine stays up); an accepted password is kept in memory for crash restarts and dropped when refused. Qt: `EngineSession::passwordRequested(wrong)`, `PasswordDialog`, `MainWindow::setPasswordProvider`.
- Note: Decision: the engine tries a typed password as typed, SASLprep-normalised and as Latin-1 (`document.rs`, `candidates`), because revision 6 requires SASLprep (ISO 32000-2 §7.6.4.3.3) and revisions 2–4 want `PDFDocEncoding` bytes; `pdfjs-saslprep-r6` and the pdfium r2/r3 files need it. New engine dependency `stringprep` (MIT/Apache-2.0, plus `unicode-normalization`, `unicode-bidi`, `unicode-properties`, `tinyvec`), see `docs/backlog.md`.
- Note: Corpus gate (`cargo test -p vellora-engine --test corpus -- --ignored --nocapture`): 265 of 275 open (96.4%), 8 of them through the password steps (asked, a wrong password refused, then the manifest's). Protected files now count in the denominator. The 10 refused are malformed (8 not-a-PDF for PDFium, 2 `bad_okey`), so the 98% of the M1 criteria is task 25's to settle.
- Note: Local: Qt test exes have no console and a `for` loop in a `.bat` did not find them; start each from PowerShell with the Qt `bin` on `PATH` and `-o file.txt,txt` (tst_main_window 13/13, tst_engine_session 8/8). Passwords stay out of logs: `tests/password.rs` runs the real engine at `trace` and searches its stderr (checked to fail when a log line leaks).

## Phase B: application shell

### - [x] Task 8: Multiple documents, opening files, settings
- **Goal:** the basics of a desktop app.
- **Do:**
  - **Document tabs** in the main window: one engine process per open document, closing a tab closes its engine. Ctrl+Tab / Ctrl+Shift+Tab, Ctrl+W, and Ctrl+Shift+T to reopen the last closed tab.

  - Unreadable/missing files from the recent list are shown greyed out with a remove action.
- **Acceptance:** Qt tests for tab lifecycle (no engine leaks after closing 50 tabs), command-line open, single-instance forwarding, and view-state restore.
- **Depends:** 1
- Note: Structure: `DocumentTab` (engine session, canvas, repair bar, password prompt, status texts) per tab, hosted by `MainWindow` in a `QTabWidget`. The window always has a tab; an empty one is reused by the next file, and a path that is already open only switches to its tab. `session()`, `canvas()` and the status texts are the current tab's, so `openDocument` in a tab that has a document now means a new tab (tests that replace a document use `tab(i).open`).

  - Protocol `GetLinks(page)` → rect + action. Action kinds: `GoTo` (destination), `URI`, `Named` (NextPage, PrevPage, FirstPage, LastPage), plus `GoToR`, `Launch`, `JavaScript`, `SubmitForm`, `ImportData` and others as **inert** kinds.
  - Hover cursor and tooltip showing the target.
  - Internal jumps go through the navigation history.
  - **URIs open only after a confirmation** showing the full URI (scheme allowlist: `http`, `https`, `mailto`; others are shown and refused). Per-document "don't ask again for this host" for the session only.
  - Inert kinds show "This link would run an action Vellora never runs (Launch / JavaScript / …)" (invariant 8).
- **Acceptance:** tests for each action type. A test asserts the engine makes no network calls (the sandbox from tasks 4–5 also enforces it).
- **Depends:** 12

### - [ ] Task 14: Text extraction, selection and copy
- **Do:**
  - Protocol `GetTextPage(page)` → characters with Unicode, box, font size and a line/word grouping. Uses PDFium's text API through `vellora-render`; ligatures are expanded, hyphenation preserved.
  - Cache per page in the engine, bounded.
  - UI:
    - text cursor over text
    - selection by drag, double-click word, triple-click line
    - Shift+click extend
    - Ctrl+A on the page or document, with a confirmation for more than 1,000 pages
    - selection across pages
    - copy as plain text (Ctrl+C) in reading order, with the column order PDFium gives
  - Right-to-left and vertical text are extracted correctly. Selection may be visually imperfect there; document the known limits.
- **Acceptance:** golden selection-rectangle tests on a fixture set. Copied text matches an independent extractor on a 30-file corpus subset, within a normalised edit distance of 2%. Use Poppler's `pdftotext` **only as an external test tool**: installed in CI, never linked or shipped, which the dependency policy allows.
- **Depends:** 10

### - [ ] Task 15: Search
- **Do:**
  - Find bar (Ctrl+F) with case-sensitive, whole-word and **regular expression** options (Rust `regex` crate, size- and time-limited).
  - Search runs in the engine at low priority, page by page, streaming `SearchHit` batches with page, quads and a context snippet. It's cancellable, and a new query cancels the old one.
  - Results panel with a count and per-hit list; F3/Shift+F3 to step; hits highlighted on the canvas; the current hit scrolled into view.
  - Text extraction is reused from task 14's cache.
- **Acceptance:** the first hit on the 10,000-page text document arrives in < 1 s, and a full scan of 1,000 pages finishes in < 3 s. Cancelling stops engine work within 100 ms (test). Frame-time test clean while searching.
- **Depends:** 14

### - [ ] Task 16: Printing
- **Goal:** a viewer must print.
- **Do:**
  - Native print dialog (`QPrintDialog`): printer, copies, page range (accepts page labels and selection), "current page", odd/even, fit to page / actual size / shrink oversized, auto-rotate and centre, grayscale option.
  - Pages are rendered by the engine at printer resolution **in bands** (tiles), so no full-page buffer exceeds the slot size, then drawn into `QPainter` on `QPrinter`. Progress dialog with cancel. Annotations render as PDFium renders them for print (the `FPDF_PRINTING` flag).
  - Honour the document's print permission (task 7) with a clear message. A print preview dialog reuses the same path at screen resolution.
  - **Print to PDF** is not offered (it would bypass our writer). Use the OS's own printer if wanted.
- **Acceptance:** a test prints a 3-page fixture to a `QPrinter` in PDF output mode (test-only use), and the result's pages, rasterised by our engine, match the source within the golden tolerance. Cancelling mid-job stops engine work.
- **Depends:** 7, 10

### - [ ] Task 17: Canvas accessibility and keyboard navigation

  - Keyboard caret browsing mode (F7) to move through text by character, word and line, with Shift to select.
  - Every command is reachable by keyboard and appears in the palette, with shortcuts shown. A test enumerates the registry and fails on any command without a title.
  - Respect system high-contrast, font scaling and reduced motion (no animated scrolling).
  - Write `docs/dev/accessibility-checklist.md` with manual NVDA and Orca steps.
- **Acceptance:** Qt accessibility tests walk the tree of a fixture document and read its text. The checklist is executed and its results recorded in the PR.
