# Milestone M11 — Release hardening: Vellora 1.0

**Goal:** turn the feature-complete pre-releases into a **1.0 that strangers can install and trust**. That means signed builds on all three OSes, audited accessibility and security, published documentation, translations, and a sustainable release process. No new features: only fixes, polish and process. Plan reference: [`PLAN.md` §L2, §K](../PLAN.md) ("v1.0 = Phases 0–10 plus macOS parity and completed accessibility and security audits"). Estimated effort: 8–12 weeks, partly gated by external parties (audits, store reviews).

**How to use this file:** the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md) and the [milestone rules](README.md#rules-for-every-milestone).

## M11 / v1.0 acceptance criteria

- [ ] No open issues labelled `release-blocker`. Every feature from M1–M10 passes its tests on Windows, Linux and macOS.
- [ ] Signed installers: Windows (decision #1), macOS notarised, Linux on Flathub. Also published to winget and as a Homebrew cask.
- [ ] Accessibility audit completed (external or documented self-audit against the checklist) on all three OSes, with no open critical findings.
- [ ] Security: OSS-Fuzz onboarding accepted or applied for; an external security review completed or scheduled with funding; PDFium built from source in CI; a CycloneDX SBOM per release.
- [ ] User manual and website published. At least 3 translations at ≥ 90% (community, via a hosted platform).
- [ ] 8-hour soak test and 100-document open/close test show no leaks or crashes.
- [ ] Release process, support policy and supported versions documented. `v1.0.0` tagged when the maintainer asks.

---

### - [ ] Task 0: Refine this milestone
- **Do:** reconcile the tasks with reality after M10. Resolve the remaining maintainer decisions (#1, #4, #5). Point [`README.md`](README.md) at M11.
- **Acceptance:** a docs-only PR.
- **Depends:** M10 complete

### - [ ] Task 1: Feature freeze and stabilisation
- **Do:** declare the freeze. Triage every open issue into `release-blocker` / `post-1.0` / `wontfix`. Fix the blockers (they may split into their own tasks below this one). Run every milestone's test suites on all three OSes and fix the platform gaps.
- **Acceptance:** zero `release-blocker` issues open. The suite matrix is green on all OSes.
- **Depends:** 0

### - [ ] Task 2: Platform parity and Windows on Arm
- **Do:** a feature-by-feature parity checklist across Windows, Linux and macOS (keyboard conventions, file associations, printing, signing key stores, OCR, sandbox). Evaluate a Windows ARM64 build (PDFium and Qt provide it): ship if green, otherwise backlog.
- **Acceptance:** checklist executed with evidence. ARM64 decision recorded.
- **Depends:** 1

### - [ ] Task 3: Accessibility audit
- **Do:**
  - Run the accessibility checklist with NVDA and JAWS (Windows), VoiceOver (macOS) and Orca (Linux), in a full keyboard-only pass, with contrast checks for all themes and 200% UI scaling.
  - Invite an external audit (accessibility organisations, community). Fix the critical findings.
- **Acceptance:** audit report linked. No open critical findings.
- **Depends:** 1

### - [ ] Task 4: Security hardening and audit
- **Do:**
  - Apply for **OSS-Fuzz** (project files, build script and the existing fuzz targets).
  - Build **PDFium from source in CI** with a pinned revision, replacing the prebuilt binaries (supply chain), keeping V8 and XFA out.
  - Re-verify every sandbox, and the gap table in the security model, on all OSes.
  - Dependency review (`cargo vet` or audits) of the full tree. A reproducible-build investigation with a report.
  - Apply for an external security audit (e.g. OSTIF, Sovereign Tech Fund or Open Technology Fund programmes) focused on the parser, redaction and signatures.
- **Acceptance:** OSS-Fuzz application submitted or accepted. PDFium source build in CI. Audit funded or scheduled, and the request is public.
- **Depends:** 1

### - [ ] Task 5: Signed distribution
- **Do:**
  - Windows signing (decision #1) for the MSI and binaries, plus a winget manifest.
  - macOS notarisation (from M6) verified for the release pipeline, plus a Homebrew cask PR.
  - Linux: Flathub submission (manifest review), with AppImage optional.
  - Release artifacts with SHA-256, signatures and an SBOM.
- **Acceptance:** each package installs on a clean VM without warnings. Store/repository submissions accepted or pending review.
- **Depends:** 2

### - [ ] Task 6: Opt-in update check
- **Do:** ADR (decision #4). Off by default; the first-run dialog asks once. When enabled, it checks GitHub Releases from the UI process at most daily, shows release notes and links to the download, and never downloads or installs automatically. The admin config file can disable it.
- **Acceptance:** tests with a fixture server. A test asserts no request is ever made when it's disabled.
- **Depends:** 1

### - [ ] Task 7: Translations
- **Do:** connect the `.ts` files to a hosted translation platform (Weblate's free OSS hosting, or as decided). Write translator docs, a glossary of PDF terms and screenshots. Recruit translators via the community. Check the RTL languages.
- **Acceptance:** at least 3 languages at ≥ 90%, shipped in the release build.
- **Depends:** 1

### - [ ] Task 8: Documentation
- **Do:**
  - Complete the user manual for every feature.
  - An **administrator guide**: silent install flags; a config file to pre-set or lock preferences, including disabling every network feature; file associations; log and crash-dump locations.
  - A troubleshooting guide.
  - Developer docs: architecture docs reconciled with the code, contributor onboarding, release process.
- **Acceptance:** docs reviewed against a checklist of every command in the registry and every CLI command (generated, CI-checked).
- **Depends:** 1

### - [ ] Task 9: Website
- **Do:** GitHub Pages (decision #5): landing page (what Vellora is, privacy promise, screenshots), downloads with checksums, the manual (mdBook), security and contributing pages. No trackers and no third-party resources.
- **Acceptance:** site live. A link check runs in CI.
- **Depends:** 8

### - [ ] Task 10: Performance and stability final pass
- **Do:**
  - Re-measure every performance target on all three OSes and fix regressions.
  - **Soak tests:** an 8-hour scripted session (open, scroll, search, annotate, save, compare, in a loop) and 100 documents opened and closed in sequence. Track memory, handle and process leaks, and crashes.
- **Acceptance:** targets met on all OSes. Soak tests are clean, with reports attached.
- **Depends:** 1

### - [ ] Task 11: Release process and policies
- **Do:**
  - `docs/dev/release-process.md`: release branches, release candidates (rc1…), changelog curation, signing steps, announcement.
  - Support policy: which versions get security fixes and for how long. Update SECURITY.md "Supported versions".
  - Semver commitments for the CLI and the JSON outputs (documented schemas).
- **Acceptance:** documents merged. A release candidate is cut through the documented process.
- **Depends:** 5, 8

### - [ ] Task 12: v1.0 acceptance run and release
- **Do:** run every M11 criterion and tick it with evidence. Publish the release candidate to testers, fix the blockers, then tag `v1.0.0` when the maintainer asks. Afterwards, write milestone files for the post-1.0 phases 11–14 from the roadmap.
- **Acceptance:** all criteria checked, with evidence.
- **Depends:** 1–11
