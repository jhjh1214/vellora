# Milestone M8 — Forms (v0.8)

**Goal:** fill professional AcroForms correctly: formatting, calculation and validation of common Acrobat scripts implemented natively **without a JavaScript engine**. Plus a visual form designer, form data exchange, flattening, and honest XFA handling ([ADR-0011](../adr/0011-xfa-out-of-scope.md)). Plan reference: [`PLAN.md` §C, §K](../PLAN.md) (phase 8). Estimated effort: 10–12 weeks.

**How to use this file:** the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md) and the [milestone rules](README.md#rules-for-every-milestone).

## M8 acceptance criteria

- [ ] On the form corpus, every fillable field type can be filled, saved incrementally and reopened with identical values and appearances, in Vellora and in Acrobat (manual checklist).
- [ ] Number, percent, date, time and special (zip, phone, SSN) formats, simple calculations (sum, average, product, min, max) and range validation behave like Acrobat on the test forms. Unknown scripts are reported per field and never run.
- [ ] The form designer creates every field type. The resulting forms fill correctly in Acrobat and PDFium.
- [ ] FDF/XFDF/JSON data import and export round-trip. Flattening produces pixel-identical static pages.
- [ ] XFA: static XFA with AcroForm fallback fills via the fallback; XFA-only documents show a clear explanation.
- [ ] Tagged pre-release `v0.8.0`, only if the maintainer asks.

## Phase A: the form model

### - [ ] Task 1: Field model and ADR "Native form filling"
- **Do:**
  - ADR: forms are filled by Vellora's own model and appearance generator; PDFium only renders the result (ADR-0002 unchanged: PDFium never holds edit state).
  - In `doc`: the field tree with inheritance:
    - `/FT`, `/Ff` flags, `/V`, `/DV`, `/DA`, `/Q`, `/MaxLen`, `/Opt`, `/TI`, `/I`, `/TU`, `/TM`
    - widgets and kids
    - radio groups and checkbox export values (from `/AP /N` state names)
    - `NeedAppearances`, `/CO` calculation order, `/AA` actions (read as data)
  - Protocol `GetFields` (paged) and per-page widget geometry.
- **Acceptance:** corpus test reading every form with no panics. Unit tests for inheritance and every field flag.
- **Depends:** 0

### - [ ] Task 2: Field appearance generation
- **Do:**
  - Text fields: single/multi-line, comb, alignment, auto font size (`0 Tf`), scrolling content clipped to the widget, padding per `/MK`, password fields shown masked.
  - Checkboxes and radios: use the existing `/AP` states, otherwise generate from `/MK /CA` with ZapfDingbats.
  - Choice fields: the combo shows the value; a list box shows the selection highlight.
  - Push buttons keep their appearance.
  - Fonts from `/DR` + `/DA` through the `fonts` crate (adding glyphs when the form's font lacks them, flagged).
- **Acceptance:** golden renders per field type and option. Fields generated by us render identically in PDFium and pdf.js within tolerance.
- **Depends:** 1

### - [ ] Task 3: Fill operations
- **Do:** ops `SetFieldValue{name, value}`, `ResetForm{fields?}`, `ImportFormData`. Each regenerates the affected appearances and clears `NeedAppearances` once all are generated. Incremental save; the `SaveImpact` notes form-fill as a DocMDP-allowed change (signatures, M9).
- **Acceptance:** unit tests. The invariant harness confirms only field objects and their widget appearances changed.
- **Depends:** 2

### - [ ] Task 4: Native Acrobat format, keystroke, calculate and validate functions
- **Do:**
  - A **recogniser** for `/AA` `/K` `/F` `/V` `/C` JavaScript bodies that consist of known Acrobat form-library calls: `AFNumber_Format/Keystroke`, `AFPercent_*`, `AFDate_FormatEx/KeystrokeEx`, `AFTime_*`, `AFSpecial_Format/Keystroke` (0–3), `AFSimple_Calculate` (SUM, AVG, PRD, MIN, MAX), `AFRange_Validate`. It tolerates whitespace and quoting variants and accepts nothing else.
  - Native implementations with locale-correct output matching Acrobat. Calculation in `/CO` order with cycle protection.
  - Any other script: no execution, plus a per-field "uses scripts Vellora doesn't run" indicator.
- **Acceptance:** a table-driven test suite of Acrobat behaviour for each function (inputs → expected outputs, documented sources). Fuzz target on the recogniser.
- **Depends:** 3

## Phase B: user interface

### - [ ] Task 5: Filling forms in the UI
- **Do:**
  - In View mode, fields become interactive. Native widgets are overlaid on field rects at the current zoom (line edit, multi-line edit, combo, list, checkbox, radio), with formatting on blur and keystroke filtering per task 4.
  - Tab order per `/Tabs` and field order; required-field highlighting; a "Highlight fields" toggle; validation messages inline (no modal popups); a clear-form command.
  - Accessible names from `/TU`.
  - Values commit as ops (batched per field edit).
- **Acceptance:** Qt tests for each widget type, tab order and formatting. Frame-time test on a 100-page form.
- **Depends:** 4

### - [ ] Task 6: Form data exchange and flattening
- **Do:**
  - Export and import field data as FDF, XFDF and JSON (XXE-safe XML).
  - `FlattenForm{fields? | all}` merges widget appearances into page content and removes the fields (destructive, shown in `SaveImpact`).
- **Acceptance:** round-trip tests. Flattened pages are pixel-identical to their filled versions.
- **Depends:** 3

### - [ ] Task 7: Form designer
- **Do:**
  - A Forms mode: draw a field (text, checkbox, radio group, combo, list, push button, signature placeholder).
  - Properties panel: name (unique-checked), tooltip, required, read-only, default value, max length, comb, multi-line, options with export values, radio group membership and export values, font, size, colours, border, and **format presets** that write the corresponding Acrobat `AF*` scripts (so Acrobat behaves the same) and use our native behaviour.
  - Align/distribute/same-size, duplicate across pages, a tab-order editor, delete.
- **Acceptance:** Qt tests for each field type. A designed form fills correctly in Acrobat (manual checklist) and in Vellora (automated).
- **Depends:** 5

### - [ ] Task 8: Automatic field detection (assistive)
- **Do:** suggest fields from page content (underscored lines, empty boxes, "Name: ____" label patterns) using the M4 page objects. Suggestions appear as dashed outlines the user accepts or rejects; nothing is created without acceptance.
- **Acceptance:** detection precision/recall ≥ 80% on a labelled set of 30 forms (report attached).
- **Depends:** 7

### - [ ] Task 9: XFA handling
- **Do:**
  - Detect static vs dynamic XFA.
  - Static XFA with an AcroForm fallback: fill through the fallback and offer `RemoveXFA` (with a `SaveImpact` warning) so other viewers don't show stale XFA data.
  - XFA-only (dynamic) documents: a clear notice per ADR-0011 with the reason and alternatives.
- **Acceptance:** fixtures for each case.
- **Depends:** 3
