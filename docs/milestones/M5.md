# Milestone M5 — Compare foundation (v0.5 = MVP)

**Goal:** the defining feature, *a pull-request review for PDFs*. Compare two versions of a document, navigate change by change (OLD/NEW), comment on changes, mark them reviewed, and export the result. Then ship the **MVP** ([ADR-0008](../adr/0008-mvp-scope.md)). This milestone creates the `diff` crate. Plan reference: [`PLAN.md` §J item 9, §K](../PLAN.md) (phase 5). Estimated effort: 8–10 weeks.

**How to use this file:** the *one task per session* protocol in [`CLAUDE.md`](../../CLAUDE.md) and the [milestone rules](README.md#rules-for-every-milestone).

## M5 acceptance criteria

- [ ] On the labelled compare corpus: **recall ≥ 95%** and **precision ≥ 90%** for text changes, with number changes classified correctly in ≥ 95% of cases.
- [ ] Text that merely reflows to another page produces no change. Inserted, deleted and moved pages are reported as page-level changes.
- [ ] Two 100-page contracts compare in < 5 s, and two 1,000-page documents in < 60 s with streaming progress and bounded memory (Windows and Linux).
- [ ] Review state (reviewed/dismissed, comments) persists in the sidecar and survives reopening. Comments are standard annotations in the new document.
- [ ] `vellora compare` produces text, Markdown and JSON reports and an annotated copy.
- [ ] MVP scope of ADR-0008 is complete. The release checklist is executed. Installers for Windows and Linux are published.
- [ ] Tagged release `v0.5.0`, only if the maintainer asks.

## Phase A: the diff engine

### - [ ] Task 1: `diff` crate: comparison text model
- **Do:**
  - New crate `crates/diff` (`vellora-diff`, pure Rust, plain data in and out, no PDF parsing). Input: per-page words with boxes and font size (from the engine's text pages).
  - Normalisation:
    - whitespace runs
    - end-of-line hyphenation joins (only when the joined word is more frequent in the document than the split form)
    - ligatures, quote and dash variants
    - optional case folding
  - Tokens: word, number (integers, decimals, thousands separators, currencies, percentages), date, punctuation, each carrying `(page, box)` provenance.
- **Acceptance:** unit tests for every normalisation and number/date form (incl. `1,000.50`, `1.000,50`, `€5`, `30%`, `2026-10-08`, `October 8, 2026`).
- **Depends:** 0

### - [ ] Task 2: Page alignment
- **Do:**
  - Page fingerprints: token shingles with MinHash. Pages without text (scans) use a downsampled-render perceptual hash from the engine.
  - Sequence alignment (dynamic programming with insert/delete costs) gives matched pages, inserted pages and deleted pages.
  - Detect **moved pages**: an unmatched page with a high-similarity match elsewhere.
  - Output an alignment used as anchors by task 3.
- **Acceptance:** tests on synthetic page shuffles, insertions and deletions, and on scanned-page fixtures.
- **Depends:** 1

### - [ ] Task 3: Document token diff
- **Do:**
  - Diff the **whole-document token stream** (not page by page), anchored by the page alignment, so text that reflows across page boundaries doesn't show up as a change.
  - Use a histogram/patience diff (`similar` crate or our own), chunked between anchors to keep time and memory bounded.
  - Map each change back to boxes on the old and new pages.
- **Acceptance:** tests: a reflow-only fixture gives 0 changes; one inserted sentence that pushes 3 pages gives exactly 1 change.
- **Depends:** 2

### - [ ] Task 4: Change model and classification
- **Do:**
  - `Change{id, kind: Insert | Delete | Replace | PageInserted | PageDeleted | PageMoved, old: {pages, boxes, text}, new: {…}, category: Text | Number | Heading | WhitespaceOnly | PunctuationOnly}`.
  - Group adjacent token edits into sentence-level changes.
  - Heading detection from font size relative to the page's body text.
  - Stable ids: a hash of the old/new text and neighbouring context, so review state survives a recompute.
  - Summary counts by category.
- **Acceptance:** unit tests per category. Ids are stable across two runs and across a run with an unrelated change elsewhere.
- **Depends:** 3

### - [ ] Task 5: Labelled compare corpus and evaluation
- **Do:**
  - Build a labelled set:
    - (a) synthetic contracts and reports generated with our writer (M4 add-text) in two versions, with known edits: words, numbers, dates, sentences, headings, inserted/deleted/moved pages, reflow-only changes
    - (b) real pairs of public documents with versions (e.g. successive IETF Internet-Draft PDFs, government forms revisions), with licenses recorded, and changes labelled by hand in a JSON sidecar
  - `cargo xtask compare-eval` computes precision, recall and number-classification accuracy, and runs in the nightly job.
- **Acceptance:** ≥ 40 labelled pairs. The evaluation runs in nightly and its report is attached to the PR.
- **Depends:** 4

### - [ ] Task 6: Compare session plumbing
- **Do:**
  - Comparing opens two documents (two sandboxed engines). The engine client fetches text pages from both and runs `vellora-diff` in a background thread **in the UI process's Rust client**. This is allowed because it's plain, size-capped data, not PDF bytes. Record that in an ADR "Where compare runs".
  - Progress events and cancellation.
  - Results are cached per pair of document identities (content hash).
- **Acceptance:** integration test on a labelled pair produces the expected changes through the client API. Cancelling stops work within 200 ms.
- **Depends:** 4

## Phase B: review experience

### - [ ] Task 7: Compare view
- **Do:**
  - *Compare documents…* (current document vs another file, or two files) opens a Compare tab:
    - side-by-side old/new views with **synchronised scrolling** through the page alignment
    - change highlights coloured by kind (inserted, deleted, replaced, number)
    - a change list with filters (category, page, hide whitespace/punctuation-only)
    - a **change card**: OLD / NEW text with intra-line highlights, and "Change 12 / 17, Page 18"
  - Keyboard: N / Shift+N (or F8 / Shift+F8) next and previous change.
- **Acceptance:** Qt tests for navigation and sync. Frame-time test on a 1,000-page comparison. A manual UX checklist with screenshots in the PR.
- **Depends:** 6

### - [ ] Task 8: Review actions and sidecar
- **Do:**
  - Per change: **Comment** (creates a standard annotation in the *new* document via M3 ops: a highlight over the new text, or a note at the location of a deletion, whose text quotes OLD → NEW; saved incrementally), **Mark reviewed**, **Dismiss**. Batch actions for a filtered selection.
  - Review progress ("Reviewed 12 / 17").
  - Sidecar `<new>.pdfreview.json`, versioned schema:
    - both documents' identities (SHA-256)
    - change ids and their states
    - timestamps
    - author (from M3 identity)
  - Opening a compare finds and applies the sidecar. If a document changed, re-compute and re-attach states by stable id, and report orphans.
- **Acceptance:** tests: review state round-trips; orphan handling; comments appear in the new PDF and in Acrobat (manual check).
- **Depends:** 7

### - [ ] Task 9: Compare reports and annotated copy
- **Do:**
  - Export a report as Markdown, HTML (self-contained, no external resources) or JSON: summary counts, page changes, every change with OLD/NEW and its review state.
  - **Annotated copy:** a new PDF (via `ops`, full write) of the new document with a highlight/strikeout annotation per change and a summary note on page 1. The originals are untouched.
- **Acceptance:** snapshot tests of the reports. The annotated copy opens in PDFium and pdf.js with one annotation per change.
- **Depends:** 8

### - [ ] Task 10: CLI `compare`
- **Do:** `vellora compare old.pdf new.pdf [--format text|md|html|json] [--annotate out.pdf] [--ignore whitespace,punctuation,case] [--pages-only]`. Exit codes: 0 no differences, 3 differences found, 1 error, 2 usage. Documented.
- **Acceptance:** CLI tests and snapshots on labelled pairs.
- **Depends:** 9

### - [ ] Task 11: Compare performance
- **Do:** profile and optimise to the targets. Benchmarks for 100-page and 1,000-page pairs added to the nightly gate. Memory bounded (streaming per anchor chunk).
- **Acceptance:** targets met on Windows and Linux. Numbers in `performance-targets.md`.
- **Depends:** 10
