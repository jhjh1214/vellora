# Contributing to Vellora

Thanks for your interest! Vellora is a long-term project. We optimise for people actually using the software, which means correctness, fidelity and security come before feature count.

## Before you start

- **Small fixes** (typos, bugs with an obvious fix, tests): just open a PR.
- **Features or behaviour changes:** open an issue first, using the *Feature request* template.
- **Architectural changes, new dependencies, file-format or protocol changes:** need an [ADR](docs/adr/) (a decision) or an [RFC](docs/rfcs/) (a larger proposal) that is accepted before the code lands.
- **Security vulnerabilities:** never open a public issue. See [SECURITY.md](SECURITY.md).

Please read [`docs/architecture/overview.md`](docs/architecture/overview.md) and [`CLAUDE.md`](CLAUDE.md). The latter contains the project's hard rules, which apply to human and AI-assisted contributions alike.

## Development setup

See [`docs/dev/setup.md`](docs/dev/setup.md).

## Making a change

1. Fork and create a branch from `main` (`feat/…`, `fix/…`, `docs/…`).
2. Keep PRs focused: one logical change per PR. Aim for fewer than ~400 changed lines excluding tests and fixtures.
3. Run the full local check before pushing:
   ```sh
   cargo fmt --all --check
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   cargo deny check          # if installed: cargo install cargo-deny
   ```
4. Update docs and ADRs in the same PR when you change a boundary or a documented behaviour.
5. Fill in the PR template, including the **save-fidelity impact** section if your change touches writing PDFs.
6. **Title your PR as a Conventional Commit** (e.g. `fix(cos): handle missing endobj`). `main` is protected and accepts only **squash merges**, so the PR title becomes the commit subject on `main`.

## Commit messages: Conventional Commits

```
<type>(<optional scope>): <summary in imperative mood>

<body: what and why, wrapped at 72 columns>

Signed-off-by: Your Name <you@example.com>
```

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`, `security`. Scopes are crate or area names: `cos`, `engine`, `cli`, `app`, `render`, `ipc`, `docs`, …

Breaking changes: add `!` after the type and a `BREAKING CHANGE:` footer.

## Developer Certificate of Origin (DCO)

All commits must be signed off. This certifies that you wrote the code or otherwise have the right to submit it under the project's license ([developercertificate.org](https://developercertificate.org/)):

```sh
git commit -s
```

We use a DCO rather than a CLA. You keep your copyright; your contribution is licensed under MPL-2.0.

## Code you didn't write

- Never paste code under GPL, AGPL or LGPL, or under unknown or "no license" terms.
- Porting from permissively licensed projects (MIT, BSD, Apache-2.0, MPL-2.0) is allowed. Keep the original copyright header and add an entry to [`NOTICE`](NOTICE).
- New dependencies must pass `cargo deny check` and be justified in the PR description. See [`docs/architecture/dependency-policy.md`](docs/architecture/dependency-policy.md).

## Test PDFs and the corpus

- Never commit PDFs you don't have the right to redistribute, or that contain personal data.
- Small synthetic fixtures (< 100 KB) generated by code may live in `tests/fixtures/`, with the generator committed alongside.
- Real-world documents go into the separate corpus repository via a manifest entry: URL, SHA-256, license, category. See [`tests/README.md`](tests/README.md).
- Malicious or crash reproducers go to the restricted security corpus, never the public repository.

## Good first areas

- CLI subcommands and output formatting
- Inspector and security-analysis checks
- Tests and fixtures for edge cases in the PDF spec
- Documentation and translations (once the UI exists)

Issues labelled `good first issue` are curated for newcomers.

## Review

- `main` is protected by repository rulesets ([`.github/rulesets/`](.github/rulesets/)):
  - PRs only, with linear history
  - all checks must pass, including DCO sign-off on every commit
  - review threads must be resolved
- PRs are merged by a maintainer after review.
- Reviewers check correctness, tests, fidelity and security implications, docs and license hygiene.
- Be kind. See the [Code of Conduct](CODE_OF_CONDUCT.md).
